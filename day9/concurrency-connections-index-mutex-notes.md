# Go 与 PostgreSQL：并发、连接池、索引和锁

本文整理三个问题：并发任务数与数据库连接数是什么关系、为什么创建索引后查询仍可能很慢，以及为什么不能只依赖 Go Mutex 保护数据库记录。

## 1. 并发数量与数据库连接数量的关系

### 1.1 并发任务可以轮流复用连接

**并发任务数不等于数据库连接数。** 多个请求或 goroutine 可以轮流使用连接池中的连接。

假设配置：

```go
config.MaxConns = 3
```

启动 10 个 goroutine，每个执行一次数据库查询：

```text
10 个 goroutine 申请连接
    ↓
最多 3 个同时持有连接，其余等待
    ↓
任务结束并归还连接
    ↓
等待的任务获取连接，继续执行
```

对于普通 pgxpool 使用方式，一个连接同一时间供一个借用者使用。复用主要是轮流使用，不是让多个 goroutine 同时在同一连接上独立执行 SQL。

| 数量 | 含义 |
| --- | --- |
| 并发任务数 | 同时存在的请求或 goroutine 数量 |
| 当前连接数 | 池中当前实际连接数量，可能小于配置上限 |
| 已借出连接数 | 当前被任务持有、尚未归还的连接数量 |
| 连接池上限 | MaxConns 指定的最大连接数 |

### 1.2 请求不一定始终占用数据库连接

解析请求、参数校验、普通计算等通常不需要数据库连接。一般在访问数据库时申请连接，用完后归还。

如果开启事务，事务通常会从 Begin 成功到 Commit 或 Rollback 结束持续占用一个连接。因此，不应在事务中进行不必要的长时间等待或外部网络调用。

查询多行时，也应及时消费结果并关闭 Rows，避免长期占用连接。

### 1.3 持有连接不等于正在有效执行

```text
连接 1：持有行锁，执行更新
连接 2：等待连接 1 释放行锁
连接 3：等待连接 1 释放行锁
```

三个连接都被占用，但后两个主要在等待。增加连接数不一定提升吞吐量，反而可能增加数据库负担和竞争。

连接数通常比并发请求数少，但这不是必须满足的规则。配置应结合 SQL 耗时、事务长度、数据库承载能力和实际等待情况判断。

部署多个实例后，还要统计连接总量。例如，每个实例 MaxConns=10，部署 5 个实例，则仅这些实例的连接上限合计就达到 50，尚未计入管理工具及其他服务。

## 2. 为什么创建索引后，查询仍可能很慢？

**索引主要降低定位记录的成本，不能消除查询中的全部工作。** 查询仍可能需要回表、排序、读取大量数据或等待锁。

### 2.1 索引不一定适合查询

假设已有索引：

```sql
CREATE INDEX idx_tasks_status_created_at
ON tasks (status, created_at DESC);
```

适合的查询示例：

```sql
SELECT *
FROM tasks
WHERE status = 'pending'
ORDER BY created_at DESC
LIMIT 20;
```

但它不能直接解决下面的标题搜索：

```sql
WHERE title LIKE '%benchmark%'
```

索引字段、顺序、类型和查询表达式都会影响使用方式。对列进行 lower(title) 等函数运算时，普通 title 索引通常也不能直接用于对应表达式查找，可能需要表达式索引或其他合适的索引方案。

### 2.2 匹配记录太多

```sql
SELECT * FROM tasks WHERE status = 'pending';
```

测试数据中约三分之一是 pending，即使通过索引找到记录，也仍需要读取和返回数千行。

如果匹配记录覆盖表的大部分页面，优化器可能认为 Seq Scan 更便宜。**全表扫描不一定意味着索引失效或计划错误。**

### 2.3 大量回表

索引只有 status 和 created_at，而 SELECT * 需要其他字段时，就需要访问表记录。

```text
索引定位记录
    ↓
到表的数据页读取其他字段
```

匹配行越多、位置越分散，回表成本可能越高。项目中曾出现的计划：

```text
Bitmap Index Scan：收集符合条件的位置
    ↓
Bitmap Heap Scan：按数据页集中回表
```

其中访问了 225 个表页，说明索引已经起作用，但并没有消除读取表数据的工作。

### 2.4 排序与深分页

如果索引不能提供 ORDER BY 所需顺序，需要额外 Sort。数据量大时，排序可能使用临时文件。

位图扫描按表页顺序回表，会丢失索引顺序，因此即使使用了索引，也可能仍需排序。

深分页示例：

```sql
SELECT * FROM tasks
ORDER BY created_at DESC
LIMIT 20 OFFSET 100000;
```

即使使用索引，也通常需要走过大量被 OFFSET 跳过的结果。与之相比，匹配索引顺序的 LIMIT 20 查询可以拿够就停。

### 2.5 缓存、统计信息和资源压力

- 数据页不在 PostgreSQL 缓存中时，需要读入，可能产生存储 I/O；shared read 不一定代表物理磁盘读取，也可能命中操作系统缓存。
- 数据大量变化后，统计信息不准确，可能导致优化器选错方案，可按需执行 ANALYZE tasks。
- 数据库 CPU、内存或存储繁忙，也会影响查询速度。
- 返回大量结果还会产生网络传输、序列化和应用处理开销。

### 2.6 慢在等待，索引无法单独解决

可能的等待包括：

- 应用等待连接池空闲连接。
- UPDATE 等待其他事务释放行锁。
- 数据库等待 I/O 或其他资源。

连接池等待发生在 SQL 提交给数据库之前，不会出现在这条 SQL 的执行计划里。

### 2.7 排查方法

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

| 观察点 | 要确认的问题 |
| --- | --- |
| 扫描方式、Index Cond | 索引是否用于定位？ |
| actual rows、被过滤行数 | 是否读取了很多不需要的记录？ |
| Sort、临时块读写 | 是否存在昂贵排序或落盘？ |
| Buffers | 访问了多少页，缓存命中还是读取？ |
| 预估 rows 与实际 rows | 是否有明显估算偏差？ |
| Execution Time 与接口总耗时 | 慢在数据库执行，还是连接池、网络或应用处理？ |

EXPLAIN ANALYZE 会真正执行 SQL；分析修改语句时也会执行修改，不能把它当作纯预览。

## 3. 为什么单纯依赖 Go Mutex 不够？

**sync.Mutex 只协调共享同一把锁的 goroutine，不会自动锁住数据库记录。**

### 3.1 单进程内必须使用同一把锁

```go
mu.Lock()
defer mu.Unlock()

// 读取并修改任务
```

只有所有相关路径使用同一把 mu，才能互相排斥。

下面的方式无法协调不同请求：

```go
func UpdateTask() {
    var mu sync.Mutex
    mu.Lock()
    defer mu.Unlock()
    // 每次调用都有独立的锁
}
```

如果使用一把全局锁包住全部任务更新，还会让不同任务的更新相互阻塞，降低并发能力。

### 3.2 多实例之间不共享锁

```text
请求 A → 服务实例 1 → Mutex 1 ─┐
                              ├→ 同一条数据库记录
请求 B → 服务实例 2 → Mutex 2 ─┘
```

不同进程有各自的内存和锁，都可能同时进入数据库更新逻辑。

脚本、后台任务、数据库客户端等其他写入路径也不会遵守 Go 进程中的 Mutex。

### 3.3 排队不等于检测旧数据

即使只有一个服务实例且正确共享锁，也可能发生：

```text
A、B 都读取到 version=1
    ↓
A 获得 Mutex，更新并释放
    ↓
B 获得 Mutex，仍按客户端旧数据更新
```

Mutex 保证了服务内执行顺序，却没有验证 B 的更新前提是否仍然成立。

乐观锁条件更新可以检测旧版本：

```sql
UPDATE tasks
SET status = $1,
    version = version + 1
WHERE id = $2 AND version = $3
RETURNING version;
```

A 成功后版本改变，B 携带旧版本便无法匹配。所有相关写入入口都应维护版本，否则可能漏掉修改。

### 3.4 各种机制解决不同问题

| 机制 | 主要作用 |
| --- | --- |
| Go Mutex | 保护单个进程内共享同一把锁的内存或代码区域 |
| 数据库悲观锁 | 跨连接、跨进程协调数据库记录访问，例如 SELECT ... FOR UPDATE |
| 数据库版本条件更新 | 原子检查版本，阻止过期数据覆盖 |
| 数据库事务 | 保证任务更新、事件插入等操作整体提交或回滚 |

数据库悲观锁也不能自动判断客户端版本是否过期，需要时仍应结合版本校验。单纯开启事务，也不代表所有并发覆盖问题都会自动消失。

## 4. 在任务项目中的对应关系

```text
并发请求进入 Go 服务
    ↓
从连接池获取连接，连接不足时等待
    ↓
数据库按执行计划定位和读取记录
    ↓
通过行锁或版本条件协调并发修改
    ↓
事务内更新任务、写入事件
    ↓
提交或回滚，归还连接
```

实际使用悲观锁、乐观锁或二者结合，取决于业务；上述步骤不是说每个请求都必须使用同一种锁方案。

- 连接池控制数据库访问资源，不能代替业务并发校验。
- 索引帮助降低查询成本，不能保证没有等待，也不保证查询一定快。
- Mutex 保护本进程中的共享状态，不能单独替代数据库一致性机制。
- 数据库事务、锁、条件更新和约束应共同承担持久化数据的一致性保护。
