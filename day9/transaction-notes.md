### 一、学到的知识点

- **事务的原子性**：更新任务状态和插入事件属于同一个操作，应该一起成功或一起回滚，避免任务状态变了却没有事件记录。
- **事务操作必须使用同一个 `tx`**：通过 `pool` 执行的 SQL 不会自动加入已经创建的事务。
- **读取旧状态用于记录变更和检查业务规则**，不是给回滚提供数据。数据库自己管理回滚，不需要应用传入旧状态。
- **`SELECT ... FOR UPDATE` 会锁住任务行**，让并发修改同一任务的事务依次处理，保证事件中的旧状态与实际更新前一致。
- **`Exec` 用于不返回结果行的 SQL**；需要读取 `RETURNING` 返回值时，使用 `QueryRow().Scan()`。
- **`return err` 也会触发 `defer`**。函数提前返回时，已经登记的 `defer tx.Rollback(ctx)` 仍然会执行。
- **`Commit` 也可能失败**，因此必须检查或返回它的错误。
- **Context 通过参数传递**：启动阶段的 Context 与 HTTP 请求的 Context 不同，超时不会自动覆盖所有后续操作。

### 二、自己写或修改的代码

实现了 `ChangeStatus`，主要流程为：

```
开始事务
→ 读取并锁定任务，取得旧状态
→ 更新任务状态
→ 构造新旧状态的 JSON 详情
→ 插入 task_events
→ 提交事务
```

配套完成了：

- 注册 `PATCH /tasks/:id` 路由。
- 定义 `ChangeStatusRequest`，接收客户端的新状态。
- 在 Service 中检查状态是否合法。
- 定义 `TaskEvent`，使用 `json.RawMessage` 表示事件详情。
- 将事件类型 `status_changed` 放入 `EventType`，将新旧状态放入 `Details`。
- 将没有 `RETURNING` 的更新语句改为 `tx.Exec()`。
- 修正插入事件 SQL 的列名：`taskid` 改为 `task_id`。
- 在事务开始成功后登记延迟回滚，并返回提交结果。

后续检查时还发现需要补齐：读取旧状态后的通用错误处理、更新 `updated_at`、Handler 对任务不存在返回 404，以及防止其他更新入口绕过事件记录。

### 三、测试现象

**正常更新实验**

用 Postman 发送新状态。验证时应同时检查：

- 请求成功。
- `tasks.status` 变成新状态。
- `task_events` 新增一条 `status_changed` 事件。
- 事件详情中的 `old_status`、`new_status` 与实际变化一致。

**失败回滚实验——重点记录**

测试前记录任务原状态和已有事件。让任务先更新成功，再插入 `event_type = ''` 的事件，故意触发 CHECK 约束。

应观察并记录：

1. **SQL 为什么报错**
   `task_events` 的 CHECK 约束要求事件类型去除空白后长度大于零，空字符串不满足要求。
2. **为什么事务回滚**
   事件插入失败后，Repository 返回错误；函数退出前执行延迟回滚，撤销同一事务中之前成功执行的任务更新。手动执行 SQL 实验时，则需要执行 `ROLLBACK` 结束失败事务。
3. **数据库最终状态**
   任务状态恢复为事务开始前的值，失败事件没有插入。
4. **如何证明没有部分更新**
   回滚结束后，重新查询任务和事件表：确认任务状态未变，并且没有本次操作新增的事件。只看 HTTP 错误响应，不能证明回滚正确。

注意：如果任务原来就是 `completed`，再更新为 `completed`，无法明显观察到恢复过程，应选择与原状态不同的新状态。

### 四、遇到的问题与解决原因

| 问题                                              | 原因                                                         | 解决方式                                               |
| ------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------ |
| `QueryRow(...).Scan()` 报 `no rows in result set` | `UPDATE` 没有 `RETURNING`，没有结果行可读；不代表更新一定没有执行 | 不需要返回字段时改用 `Exec`                            |
| 插入事件提示列不存在                              | SQL 使用了 `taskid`，实际列名是 `task_id`                    | 按表结构修正列名                                       |
| 字符串不能赋给 `Details`                          | `Details` 是 `json.RawMessage`，不是 `string`                | 事件类型赋给 `EventType`；详情通过 `json.Marshal` 构造 |
| 出现 `current transaction is aborted`             | 前一条 SQL 已失败，事务进入失败状态，后续普通 SQL 不能继续执行 | 找到最初错误，执行 `ROLLBACK` 后重新开始               |
| Postman 只显示“内部错误”                          | Handler 将详细错误写入服务端日志，给客户端返回统一信息       | 查看终端日志，或在断点中检查 `err`                     |
| 担心 `return err` 跳过回滚                        | 误以为返回后不会执行延迟调用                                 | 理解 `defer` 在函数退出前执行                          |
| 零影响行数时直接 `return err`                     | 此时 `err` 可能是 `nil`，会造成错误地报告成功                | 分开判断错误与影响行数，零行时按业务返回明确错误       |
| 认为 `main` 的 5 秒超时作用于请求                 | 不同操作使用了不同的 Context                                 | 在 Handler 中基于请求 Context 设置超时，并向下传递     |

另外，失败事件插入即使被回滚，也可能消耗一个自增 ID。**事件 ID 出现间隔不代表有记录残留，更不能用来判断是否发生部分更新。**
